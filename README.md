# Graph NL-to-SQL — Siemens Industrial Manufacturing POC

Natural language querying across two databases — no ERD provided, relationships auto-inferred from instance data, semantic ontology built via schema-automator + human annotation, SQL generated by Claude Haiku.

---

## What this does

You type a plain English question. The agent figures out which tables are involved, resolves the join path across two databases, generates SQL, executes it, and returns results with a chart config — all without any hardcoded schema knowledge.

**Example queries that work today:**
- *"Which machine types have the highest average downtime hours?"*
- *"Which plants have the most critical maintenance issues?"*
- *"Which machines have both high repair costs and high defect rates?"* — 3-table cross-DB join

---

## Architecture

```
Raw CSVs
    ↓ generate.py
operations.db (SQLite)       quality.db (SQLite)
    ↓ schema_profiler_local.py
relationships.json + schema_context.json
    ↓ schema_graph.py
schema_graph.png  (structural graph)
    ↓ schemauto CLI
siemens_schema.yaml  (LinkML schema — types, enums, FKs from instance data)
    ↓ generate_ontology_draft.py
ontology_draft.json  (human-annotatable semantic ontology)
    ↓  [domain expert reviews AUTO_PROPOSED edges]
    ↓ semantic_inferrer.py
semantic_graph.png  (semantic graph — business entities + named relationships)
    ↓ query_agent.py
NL → SQL → DataFrame + chart config
```

## Databases

Two SQLite databases simulating separate Snowflake schemas:

| DB | Schema | Tables | Rows |
|---|---|---|---|
| `operations.db` | operations | `machines` | 500 |
| `operations.db` | operations | `maintenance_logs` | 100,000 |
| `operations.db` | operations | `parts_inventory` | 100,000 |
| `quality.db` | quality | `production_batches` | 100,000 |
| `quality.db` | quality | `defect_reports` | 100,000 |

**Cross-DB relationships (auto-inferred, no ERD):**
- `maintenance_logs.machine_id` → `machines.machine_id`
- `parts_inventory.machine_id` → `machines.machine_id`
- `production_batches.machine_id` → `machines.machine_id`
- `defect_reports.batch_id` → `production_batches.batch_id`
- `defect_reports.part_id` → `parts_inventory.part_id`

## File Reference

| File | Input | Output | Purpose |
|---|---|---|---|
| `generate.py` | — | `data/*.csv`, `operations.db`, `quality.db` | Generates synthetic Siemens manufacturing data with referential integrity |
| `schema_profiler_local.py` | `operations.db`, `quality.db` | `relationships.json`, `schema_context.json` | Profiles both DBs, infers FK relationships via name match + value overlap |

## Running the pipeline

Run these in order. Each step depends on the previous one's output.

### Step 1 — Generate data

```bash
python generate.py
```

Outputs `data/*.csv`, `operations.db`, `quality.db`.

> To scale to 1M rows: open `generate.py` and change `N = 100_000` to `N = 1_000_000`. Then add indexes after loading (see Scaling section below).

---

### Step 2 — Profile schemas and infer relationships

```bash
python schema_profiler_local.py
```

Outputs `relationships.json` and `schema_context.json`.

> **Note:** `defect_reports` FKs (`batch_id`, `part_id`) have near-zero overlap because all IDs are unique. These are patched manually inside the script — this is expected and documented. In real ETL data on Snowflake, these would surface automatically.

---

### Step 3 — Build structural graph

```bash
python schema_graph.py
```

Outputs `schema_graph.png` — tables as nodes, FK columns as edges, cross-DB joins in red dashed lines.

---

### Step 4 — Run schema-automator

```bash
pip install schema-automator

schemauto generalize-tsvs data\machines.csv data\maintenance_logs.csv data\parts_inventory.csv data\production_batches.csv data\defect_reports.csv --column-separator "," -o siemens_schema.yaml
```

Outputs `siemens_schema.yaml` — formal LinkML schema with inferred types, enumerations, and identifiers from instance data alone. No metadata or ERD required.

> The `quantulum3` warning about classifier dependencies is harmless — ignore it.

> If schema-automator runs out of memory on 1M row CSVs, sample first:
> ```bash
> head -n 50001 data\maintenance_logs.csv > data\maintenance_logs_sample.csv
> ```
> Then run `generalize-tsvs` on the `_sample` files. The schema is identical — only value distributions are needed, not full row counts.

---

### Step 5 — Generate ontology draft

```bash
python generate_ontology_draft.py
```

Outputs `ontology_draft.json` — semantic ontology with 5 entity nodes and 6 auto-proposed relationship edges.

---

### Step 6 — Human annotation (domain expert step)

Open `ontology_draft.json` in VS Code. Search for `AUTO_PROPOSED`. For each edge:

1. Review the `relationship` verb (e.g. `LOGGED_FOR`, `CAUSED_BY`, `PRODUCED_BY`)
2. Confirm or change it to a more domain-accurate verb
3. Update `annotation_status` from `"AUTO_PROPOSED"` to `"REVIEWED"`
4. Optionally enrich the `description` field

**Current auto-proposed edges:**

| From entity | Relationship | To entity | Join key | Cross-DB |
|---|---|---|---|---|
| MaintenanceEvent | LOGGED_FOR | Machine | machine_id | No |
| Part | COMPATIBLE_WITH | Machine | machine_id | No |
| ProductionBatch | PRODUCED_BY | Machine | machine_id | Yes |
| ProductionBatch | OCCURS_AT | Machine | plant_id | Yes |
| DefectReport | BELONGS_TO | ProductionBatch | batch_id | No |
| DefectReport | CAUSED_BY | Part | part_id | Yes |

Once reviewed, the file can be renamed to `ontology.json`. Update the `ONTOLOGY_FILE` constant in `semantic_inferrer.py` and `query_agent.py` accordingly.

---

### Step 7 — Build semantic graph

```bash
python semantic_inferrer.py
```

Outputs `semantic_graph.png` — business entities as nodes, named relationships as edges. Edges marked `*` are still `AUTO_PROPOSED` and pending annotation.

---

### Step 8 — Run the query agent

```bash
python query_agent.py
```

Runs 5 test queries and prints SQL, row count, chart config, and a data preview for each.

To use interactively, import `run_query` in your own script:

```python
from query_agent import run_query

result = run_query("Which suppliers' parts appear most in defect reports?")
print(result["sql"])
print(result["data"])
print(result["chart"])   # {"type": "bar", "x": "...", "y": "...", "title": "..."}
```

## How the agent works

```
NL query
    ↓
Semantic context injected into prompt
(entities, named relationships, exact enum values, join paths)
    ↓
Claude Haiku → returns JSON: { sql, chart, explanation }
    ↓
SQLite ATTACH — operations.db attaches quality.db as "quality"
    ↓
Cross-DB SQL executes natively
    ↓
DataFrame + chart config returned
```

**Key rule for SQL generation:**
- `operations` tables: no prefix — write `machines`, `maintenance_logs`, `parts_inventory`
- `quality` tables: always prefix — write `quality.production_batches`, `quality.defect_reports`

## Scaling to 1M rows

1. In `generate.py`, change `N = 100_000` → `N = 1_000_000`
2. Re-run `python generate.py`
3. Add indexes after loading to keep joins fast:

```python
# create_indexes.py — run once after generate.py
import sqlite3

ops = sqlite3.connect("operations.db")
ops.execute("CREATE INDEX IF NOT EXISTS idx_mlog_machine ON maintenance_logs(machine_id)")
ops.execute("CREATE INDEX IF NOT EXISTS idx_parts_machine ON parts_inventory(machine_id)")
ops.execute("CREATE INDEX IF NOT EXISTS idx_parts_supplier ON parts_inventory(supplier_id)")
ops.close()

qua = sqlite3.connect("quality.db")
qua.execute("CREATE INDEX IF NOT EXISTS idx_batch_machine ON production_batches(machine_id)")
qua.execute("CREATE INDEX IF NOT EXISTS idx_defect_batch ON defect_reports(batch_id)")
qua.execute("CREATE INDEX IF NOT EXISTS idx_defect_part ON defect_reports(part_id)")
qua.close()

print("Indexes created.")
```

## Snowflake migration

When moving from local SQLite to Snowflake:

| What changes | How |
|---|---|
| DB connections in `query_agent.py` | Swap `sqlite3.connect` + `ATTACH` for `snowflake.connector.connect` |
| Schema profiler | Use `schema_profiler.py` (Snowflake version) instead of `schema_profiler_local.py` |
| SQL prefix rules | Drop the `quality.` prefix rule — Snowflake handles cross-schema joins natively via `schema.table` notation |
| schema-automator | Point at Snowflake via SQLAlchemy: `schemauto import-sql snowflake+snowflake://...` |

Everything else — `schema_graph.py`, `generate_ontology_draft.py`, `semantic_inferrer.py`, `ontology_draft.json` — is identical.

## Graph outputs explained

**`schema_graph.png`** — structural  
Tables as nodes, FK column names as edge labels. Blue = same-DB join. Red dashed = cross-DB join. Node size reflects row count. Built from `relationships.json` — pure structural inference, no semantics.

**`semantic_graph.png`** — semantic ontology  
Business entities as nodes (`Machine`, `MaintenanceEvent`, `Part`, `ProductionBatch`, `DefectReport`). Named relationships as edges (`LOGGED_FOR`, `CAUSED_BY`, `BELONGS_TO`). Built from `ontology_draft.json` after human annotation. Edges marked `*` are still pending review.
